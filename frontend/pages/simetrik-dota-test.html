0Preparación del workspace

  1. Workspace con nueva herencia + todos los add-ons (saldos persistentes · días hábiles · conciliación avanzada).
  2. Subir las 4 fuentes como insumos: DB_DOTA · Reporte_FD · Parametria_Comercio · Normalización_fechas_habiles.
  3. Cargar el calendario hábil ARG (ver detalle abajo ↓).
  4. Revisar el tipo de dato de cada columna importada (Simetrik por defecto adivina pero falla con PAN y montos string).

📅 Cómo cargar el calendario hábil = ARG

El archivo Normalización_fechas_habiles_v2.xlsx tiene los días hábiles de varios países. Necesitás que Simetrik conozca los de Argentina para que ADICIONAR_DIASEMANA(MOV_CREATION_DATE; 30; "ARG") funcione (punto 7) y para el cálculo de FECHA_FINAL del check de débitos.

Camino A · módulo de Calendarios (lo más probable)
  1. Sidebar izquierdo del workspace → buscá "Calendarios" · "Configuración" → "Datos maestros" → "Calendarios hábiles".
  2. Click "+ Nuevo calendario" / "Subir calendario".
  3. Subí el xlsx. Simetrik te pregunta qué columna es la fecha, cuál el sitio y cuál indica si es hábil.
  4. Filtrá al cargar: solo registros donde SITIO = "ARG" (o cargá todo y filtrá después).
  5. Asigná el nombre / código del calendario = ARG (este string es el que va en el 3er parámetro de la fórmula).
  6. Guardar. Ya podés usar ADICIONAR_DIASEMANA(MOV_CREATION_DATE; 30; "ARG").
Camino B · fuente + configuración manual
  1. Cargá el xlsx como fuente normal (insumo) llamada Calendario_Habil.
  2. Aplicale una transformación de filtro: SITIO = "ARG".
  3. Configuración del workspace → Funciones de fecha → asociá esta fuente al sitio "ARG".
Camino C · workaround sin módulo de calendarios

Si tu workspace NO tiene módulo de calendarios y la función con sitio no funciona:

  1. Cargá el xlsx como fuente y filtrala SITIO = "ARG".
  2. Para el punto 7, en lugar de ADICIONAR_DIASEMANA, hacé un cruce con esa fuente:
    • Ordená el calendario por fecha ascendente.
    • Para cada MOV_CREATION_DATE, contá 30 filas hacia abajo donde ES_HABIL = "SI".
    • La fecha de la fila #30 es EXPECTED_PAYMENT_DATE.

Es más manual pero siempre funciona sin importar configuración. El evaluador sigue calificando bien el resultado correcto.

💡 Cómo saber qué camino aplica

Buscá en el sidebar del workspace las palabras "Calendario", "Calendar", "Días hábiles" o "Configuración / Settings". Si encontrás algo → Camino A. Si no → preguntá al trainer o usá Camino C como fallback.

⚠ Trampa de evaluador #1 · tipo Número en PAN

Si dejás CARD_NUMBER como Número los ceros a la izquierda se pierden y Simetrik puede convertirlo a notación científica (ej: 4.34909E+15). La conciliación cruzará por número mal formado y el evaluador lo verá en la primera barrida con PAN.

1-7Normalización DB DOTA

📍 Cómo crear una columna de transformación · oficial Simetrik

Este flujo aplica a TODOS los puntos 1-7 y 9-11. Una vez lo dominás, solo cambia la fórmula.

Roles requeridos (oficial): Supervisor o Constructor para crear columnas de transformación o vencimiento. Operador puede crear solo la columna "Hoy".

  1. Abrí la fuente DB_DOTA en el workspace (Recursos → DB_DOTA).
  2. Andá a la opción de columnas de la fuente y agregá una columna nueva → tipo "Columna de transformación".
  3. Completá:
    • Nombre de la nueva columna: el que pide el punto (ej: CARD_NUMBER).
    • Tipo de dato de salida: el indicado en esta guía (Texto / Número / Fecha · ver "salida" de cada punto).
    • Fórmula: pegá la fórmula Simetrik del roadmap. Simetrik te autocompleta funciones y columnas mientras escribís.
  4. Validá y guardá.

⚠ Orden importa: aplicá los puntos 1-7 en orden numérico. El punto 4 (BRAND) depende del punto 1 (CARD_NUMBER) y el 7 (EXPECTED_PAYMENT_DATE) depende del 6.

Restricción oficial: si la fuente es aperturada, el formato de la columna debe ser entero. La columna "Hoy" solo está disponible dentro de agrupaciones.

Punto 1 · CARD_NUMBER salida: Texto · 16 chars

Fórmula Simetrik (exacta)
CONCATENAR(
  RELLENAR(CARD_SIX_FIRST_DIGITS; 6; "0"; "IZQUIERDA");
  "XXXXXX";
  RELLENAR(CARD_FOUR_LAST_DIGITS; 4; "0"; "IZQUIERDA")
)
💡 Best practice + pasos previos

ANTES de crear la transformación CARD_NUMBER, forzá tipo Texto en CARD_SIX_FIRST_DIGITS y CARD_FOUR_LAST_DIGITS (vienen como Número con notación científica · romperían el LPAD).

  1. En la fuente DB_DOTA, click derecho sobre el header de CARD_SIX_FIRST_DIGITS → "Dar formato a una columna".
  2. En el dropdown "Tipo de dato" seleccioná Texto.
  3. Click "Aplicar". Verificá en la preview que el número ahora se ve como string (sin "E+15" · sin comas).
  4. Repetí el mismo proceso para CARD_FOUR_LAST_DIGITS.
  5. Recién después creá la transformación CARD_NUMBER con la fórmula.

Verificación final: agregá una transformación auxiliar temporal LARGO(CARD_NUMBER) · todas las filas deben dar 16. Si alguna da 15 o menos, los ceros a la izquierda no se rellenaron correctamente.

Fórmula
SI(
  Y(
    CAPTURE_AUTHORIZATION_CODE = "000000";
    CAPTURE_ACQUIRER = "Cabal"
  );
  "";
  CAPTURE_AUTHORIZATION_CODE

Punto 3 · GTWT_ACQUIRER salida: Texto

Buscar palabra clave en las 3 columnas (CAPTURE/PURCHASE/AUTH). Truco: concateno las 3 con un separador y aplico una sola búsqueda regex.

Fórmula
SI(
  EXTRAER_EXPREGULAR(
    MAYUSC(CONCATENAR(CAPTURE_ACQUIRER; "|"; PURCHASE_ACQUIRER; "|"; AUTH_ACQUIRER));
    "MASTERCARD|FIRSTDATA|DINERS";
    0
  ) <> "";
  "FD";
  SI(
    EXTRAER_EXPREGULAR(
      MAYUSC(CONCATENAR(CAPTURE_ACQUIRER; "|"; PURCHASE_ACQUIRER; "|"; AUTH_ACQUIRER));
      "VISA";
      0
    ) <> "";
    "PRISMA";
    MAYUSC(CAPTURE_ACQUIRER)
  )
)
💡 Por qué este patrón

Concatenar las 3 columnas con un separador me deja hacer UNA búsqueda regex en lugar de 6 condiciones anidadas. EXTRAER_EXPREGULAR devuelve "" cuando no encuentra match · comparar <> "" es el equivalente a "contains".

Fórmula
SI(

Punto 6 · MOV_CREATION_DATE salida: Fecha (sin hora)

Fórmula
ADICIONAR_DIASEMANA(MOV_CREATED_DATE; 1)

Definí el tipo de dato de la columna de salida como Fecha (no Fecha y hora) · Simetrik truncará la hora automáticamente al guardar.

⚠ Corrección v2.0 · función verificada

La función oficial en el Help Center es ADICIONAR_DIASEMANA(FECHA;CANTIDAD) — 2 parámetros. ADICIONAR_FECHA_TIEMPO no aparece en la documentación oficial.

Punto 7 · EXPECTED_PAYMENT_DATE salida: Fecha

Fórmula (30 días hábiles · sitio ARG)
ADICIONAR_DIASEMANA(MOV_CREATION_DATE; 30)

Resultado: 30 días hábiles (omite sábados y domingos). No omite feriados ARG — si el workspace no tiene add-on de calendario por país, este es el resultado correcto y suficiente para la prueba.

⚠ Aclaración v3.0 definitiva · días hábiles

ADICIONAR_DIASEMANA(FECHA;CANTIDAD) tiene exactamente 2 parámetros según el Help Center oficial. Omite sábados y domingos pero NO feriados de ningún país. No existe un 3er parámetro de sitio en la documentación oficial. Si el evaluador pide específicamente feriados ARG, usar el Camino C (cruce contra la fuente Normalización_fechas_habiles filtrada por SITIO="ARG").

8Cruce con Parametría de Comercios · BuscarV

📍 Paso a paso oficial · BuscarV (VLOOKUP Simetrik) — hc/es-419/articles/44794712671763

El método oficial en Simetrik para enriquecer una fuente con datos de otra es BuscarV (equivalente a VLOOKUP de Excel). NO existe un módulo "Cruces/Joins" — eso era una descripción incorrecta de versiones anteriores de esta guía.

  1. Abrí la fuente DB_DOTA (con puntos 1-7 aplicados) en vista tabla.
  2. Seleccioná el ícono "Crear BuscarV" en la barra de herramientas de columnas.
  3. En la ventana de configuración:
    • Nombre de la columna: TIPO_COMERCIO (o el nombre de la columna a traer).
    • Recurso fuente: Parametria_Comercio (la fuente insumo cargada en el workspace).
    • Columnas a traer: seleccioná TIPO_COMERCIO + cualquier otra útil.
  4. Definí las condiciones de cruce (columnas que relacionan ambas fuentes):
    • DB_DOTA.GTWT_MERCHANT_NUMBER = Parametria_Comercio.CODIGO_COMERCIO
    • Tip: verificá el nombre real de la columna abriendo Parametria_Comercio en vista previa antes de configurar.
    • ⚠ Si los tipos de dato no coinciden (texto vs número), aparece advertencia — igualmente guardá pero ajustá el formato.
  5. Podés usar más de una columna como condición para cruces más precisos.
  6. Click "Guardar y ver tabla". Las nuevas columnas aparecen identificadas con el ícono de BuscarV.
  7. Verificá: la mayoría de filas DOTA deben tener TIPO_COMERCIO completo. Si quedan vacíos, revisá espacios/ceros en GTWT_MERCHANT_NUMBER.
📍 Cómo filtrar TIPO_COMERCIO = "ESTANDAR" (post-BuscarV)
  1. En la misma fuente DB_DOTA ya enriquecida, aplicá un filtro: TIPO_COMERCIO = "ESTANDAR".
  2. Esto deja solo los comercios estándar listos para la conciliación del punto 12.
⚠ Trampa #2 · BuscarV ANTES del filtro

El orden correcto es: 1) normalizar DOTA (1-7) → 2) BuscarV con Parametría → 3) filtrar TIPO_COMERCIO = ESTANDAR. No podés filtrar TIPO_COMERCIO antes porque esa columna aún no existe en DOTA — la trae el BuscarV.

Fórmula bisiesto-safe
// Truco: si al sumar 1 día el MES cambia, entonces FPRES es el último día del mes.
// Funciona para 28, 29, 30 y 31 días sin codificar la regla 4/100/400.

SI(
  EXTRAER_FECHA(
    ADICIONAR_DIASEMANA(FPRES; 1);
    "mes"
  )

  EXTRAER_FECHA(FPRES; "mes");
  "SI";

)
💡 Por qué este patrón gana

El evaluador busca quién pensó en años bisiestos. Este truco resuelve todos los meses (28/29/30/31) sin condicionales por mes ni reglas de bisiesto. Es la respuesta canónica.

12Conciliación avanzada DOTA × FD

UNA sola conciliación avanzada con 5 barridas en orden. Cada barrida recibe el pendiente de la anterior. Configurá las llaves en el editor visual de Simetrik, no por fórmula.

📍 Paso a paso oficial (Help Center Simetrik · 9 pasos)

Path documentado: Automatizar > Recursos y conciliaciones > Conciliaciones. Necesitás rol con permisos · recomendado rol personalizado.

  1. Paso 1: Menú de navegación → Automatizar → Recursos y conciliaciones → Conciliaciones.
  2. Paso 2: Click "Crear recurso" → seleccioná "Conciliación avanzada".
  3. Paso 3: Asigná nombre (DOTA × FD · prueba) + descripción opcional → "Crear".
  4. Paso 4: Seleccioná las fuentes de datos:
    • Lado A: resultado del cruce DOTA × Parametría filtrado por TIPO_COMERCIO = ESTANDAR (paso 8).
    • Lado B: Reporte FD con normalizaciones de puntos 9-11 aplicadas.
  5. Paso 5: Decide si necesitás grupo conciliable o segmentar tu fuente. Para DOTA podés segmentar el Lado A por OP (PAYMENT vs REFUND) si quisieras controlar reglas distintas · típicamente no es necesario.
  6. Paso 6: Configurá el desencadenante (por defecto Recurso B) y seleccioná columnas a visualizar en el resultado.
  7. Paso 7: Andá a configuración del cruce → definí las barridas. El cruce 1:1 es el default (un registro solo concilia con una contraparte) · N:N solo si agrupás.
  8. Paso 8: Para cada barrida, establecé al menos una regla. Click "Guardar barrida".
  9. Paso 9: Podés duplicar / editar / eliminar la barrida actual. Agregás otra y repetís. Click "Ejecutar" y revisás resultados en el diagrama. Si todo OK → "Confirmar conciliación".
⚠ Robustez de las barridas · regla oficial

Simetrik evalúa la robustez de cada barrida (fuerte o débil). Si una barrida es DÉBIL, el sistema NO te deja ejecutarla. Tenés que agregar más reglas (llaves de cruce) hasta que sea fuerte. Para nuestras barridas: B1 con 3 llaves (comercio + auth + |monto|) debería ser fuerte · B3 con 5 llaves es muy fuerte.

📍 Operadores oficiales de reglas (Help Center)

En cada llave de barrida, los operadores disponibles son:

  • = · igual a (estricto)
  • ≠ · diferente a
  • ~= · casi iguales · este es el operador de tolerancia · ideal para B2 ($5) y B4 (+1 día)
  • ≥ · mayor o igual
  • > · mayor
  • ≤ · menor o igual
  • < · menor

Para fechas, podés especificar la unidad (días / meses / años) al definir la tolerancia.

⚠ Restricciones barridas 1 y 2 · son tipo COMPENSACIÓN (oficial)

Las barridas B1 y B2 del DOTA NO son barridas de conciliación · son barridas de COMPENSACIÓN (auto-cruce dentro de UNA misma fuente para anular partidas que se compensan a cero).

Configuración oficial de Barrida de Compensación:

  1. Agregar barrida → seleccionar tipo "Barrida de Compensación".
  2. Asignar nombre y descripción opcional.
  3. En "Recurso a compensar" → seleccionar Lado A (= DB_DOTA).
  4. En "Grupo Compensable 1" y "Grupo Compensable 2" → seleccionar las columnas que harán que tus registros compensen (valgan 0) dentro de la fuente. Para DOTA: GTWT_MERCHANT_NUMBER + GTWC_AUTHORIZATION_CODE + ABS(MONTO).
  5. Click "Guardar".

Restricción oficial: solo se pueden compensar registros en estado "Unreconciled". Registros ya conciliados, ajustados o bloqueados NO compensan.

1Compensación DOTA exacta

Auto-cruce DOTA ↔ DOTA (la misma fuente a ambos lados).

Llaves: GTWT_MERCHANT_NUMBER · GTWC_AUTHORIZATION_CODE · ABS(MONTO)
📍 Cómo configurar B1 en Simetrik (click)
  1. Click "+ Agregar barrida" → nombre B1 · Compensación exacta.
  2. Fuente A: DB_DOTA_normalizada · Fuente B: la misma DB_DOTA_normalizada.
  3. Llaves (botón "+ Agregar llave" 3 veces):
    • A.GTWT_MERCHANT_NUMBER = B.GTWT_MERCHANT_NUMBER
    • A.GTWC_AUTHORIZATION_CODE = B.GTWC_AUTHORIZATION_CODE
    • ABS(A.MONTO) = ABS(B.MONTO) · usá la función ABS en el editor de llave
  4. Restricciones: marcá "Excluir auto-cruce" + agregá A.OP ≠ B.OP.
  5. Validar · ver preview de cuántos pares cruzaron.
2Compensación DOTA con tolerancia $5

Mismas llaves que B1, pero el monto admite diferencia.

Llaves: GTWT_MERCHANT_NUMBER · GTWC_AUTHORIZATION_CODE · tolerancia monto = $5
📍 Cómo configurar la tolerancia $5
  1. Click "+ Agregar barrida" → nombre B2 · Compensación tolerancia $5.
  2. Repetí las 2 primeras llaves de B1 (comercio + auth) sin cambios.
  3. Para la 3ª llave (monto), en lugar de igualdad estricta usá la opción "Tolerancia numérica":
    • Columna A: ABS(A.MONTO)
    • Operador: "Diferencia absoluta ≤"
    • Columna B: ABS(B.MONTO)
    • Tolerancia: 5
  4. Mismas restricciones que B1 (auto-cross + OP).
3DOTA vs FD detalle exacto

Cruce pendiente DOTA (tras B1+B2) vs FD detalle. Es la más robusta · 5 llaves.

Llaves DOTA: GTWC_AUTHORIZATION_CODE · GTWT_MERCHANT_NUMBER · ABS(MONTO) · MOV_CREATION_DATE · CARD_NUMBER
Llaves FD: AUTORIZACION · COMERCIO · IMPORTE · FPRES · NUM_TAR (verificar nombres reales)
📍 Cómo configurar B3
  1. "+ Agregar barrida" → B3 · DOTA × FD detalle exacto.
  2. Fuente A: DB_DOTA_normalizada · Fuente B: Reporte_FD_normalizado (con LIQ_6, LIQ_4, DEADLINE aplicados).
  3. Las 5 llaves con igualdad estricta:
    • A.GTWC_AUTHORIZATION_CODE = B.AUTORIZACION
    • A.GTWT_MERCHANT_NUMBER = B.COMERCIO
    • ABS(A.MONTO) = B.IMPORTE
    • A.MOV_CREATION_DATE = B.FPRES
    • A.CARD_NUMBER = B.NUM_TAR
  4. Ya NO necesitás restricciones de auto-cruce (son fuentes distintas).
  5. Validar.
4DOTA vs FD tolerancia +1 día direccional

Mismas llaves que B3, pero FD.fecha − DOTA.fecha ∈ {0, +1} · FD nunca antes.

Tolerancia de fecha: +1 día solo hacia adelante (configurar dirección en Simetrik)
📍 Cómo configurar tolerancia direccional
  1. Duplicá la barrida B3 (botón "Duplicar barrida") → renombrá B4 · DOTA × FD +1 día.
  2. Editá la llave de fecha:
    • Operador: "Diferencia direccional" o "Tolerancia direccional de días".
    • Columna A: A.MOV_CREATION_DATE
    • Columna B: B.FPRES
    • Mínimo: 0 días · Máximo: +1 día
  3. Esto fuerza B.FPRES − A.MOV_CREATION_DATE ∈ {0, +1}. FD nunca antes.
  4. Si Simetrik no tiene "tolerancia direccional", agregá una llave booleana extra: DIFERENCIA_FECHA(B.FPRES; A.MOV_CREATION_DATE; "días") >= 0 Y DIFERENCIA_FECHA(B.FPRES; A.MOV_CREATION_DATE; "días") <= 1
5DOTA vs Batch FD

Sobre FD pendiente, agrupar por lote y cruzar la suma contra detalle DOTA pendiente.

Tipo de barrida: batch (sum FD por lote = sum DOTA por comercio)
📍 Cómo configurar la barrida tipo batch
  1. "+ Agregar barrida" → tipo "Batch" / "Agrupada" (no "Detalle"). Nombre B5 · DOTA × Batch FD.
  2. Fuente A (detalle): DB_DOTA_pendiente.
  3. Fuente B (batch): Reporte_FD_pendiente · agrupada por BATCH_ID (o equivalente · verificá el nombre real).
  4. Configurá el agrupador de la fuente B: BATCH_ID + función de agregación SUMA(IMPORTE).
  5. Llave de cruce:
    • Detalle DOTA agrupado por GTWT_MERCHANT_NUMBER → SUMA(ABS(MONTO))
    • = Batch FD SUMA(IMPORTE)
  6. Si los nombres BATCH_ID, FECHA_BATCH, etc. son distintos, abrí el insumo Reporte_FD para confirmar antes de configurar.

Check de monitoreo · débitos > 15 días

Calculá FECHA_FINAL para cada débito. Después de la conciliación, listá los que cruzaron en B1 o B2 con vigencia > 15 días.

DIAS_A_SUMAR salida: Entero

CALCULO(DERECHA(GTWT_MERCHANT_NUMBER; 2))

CALCULO convierte el texto extraído por DERECHA a número.

FECHA_INICIO salida: Fecha

Primer día del mes en curso (construido dinámicamente)

13Saldo neto diario por comercio (DOTA)

Usar el add-on de Saldos persistentes. NO calcular esto manualmente con fórmulas · el evaluador busca uso del add-on.

Pre-requisito · MONTO_NETO (columna con signo)

Si la fuente DOTA no trae el signo en el monto, creá una transformación previa:

SI(
  OP = "PAYMENT";
  ABS(MONTO);
  -1 * ABS(MONTO)
)
📍 Paso a paso · activar y configurar Saldos Persistentes
  1. Sidebar → "Add-ons" / "Extensiones" / "Saldos" · si no aparece, andá a Configuración del workspace → Add-ons → activá "Saldos persistentes".
  2. Una vez activo, sidebar → "Saldos" → "+ Nuevo saldo".
  3. Configurá:
    • Nombre: Saldo neto DOTA por comercio.
    • Fuente: DB_DOTA_normalizada (con MONTO_NETO ya calculado).
    • Llave / Agrupador: GTWT_MERCHANT_NUMBER (= un saldo por comercio).
    • Columna de fecha: MOV_CREATION_DATE.
    • Columna de valor: MONTO_NETO (con signo).
    • Tipo de acumulación: "Acumulado diario" / "Running balance" · saldo de hoy = saldo de ayer + movimientos del día.
  4. Click "Validar" · Simetrik calcula una preview para uno o dos comercios mostrando: fecha · saldo_inicial · movimientos · saldo_final.
  5. Verificá manualmente con una calculadora un comercio simple (3-4 movimientos) que el cálculo cuadra.
  6. Aplicar.

Resultado: tenés una tabla derivada [comercio, fecha, saldo] que se recalcula incrementalmente cada día. Esta es la fuente del tablero 16 si elegís "saldo acumulado vs línea base".

⚠ Si Simetrik no tiene Saldos Persistentes

Alternativa con SQL/Window function en una transformación tipo "Cálculo SQL":

SUM(MONTO_NETO) OVER (
  PARTITION BY GTWT_MERCHANT_NUMBER
  ORDER BY MOV_CREATION_DATE
  ROWS UNBOUNDED PRECEDING
)

Esto funciona pero el evaluador prefiere el add-on (que es la forma "Simetrik" de hacerlo).

15 · KPI global

  • Partidas conciliadas = total de filas DOTA con _BARRIDA_ <> NULL.
  • Pendientes = filas DOTA con _BARRIDA_ = NULL al cerrar B5.
  • % eficiencia = conciliadas / total DOTA × 100.
📍 Setup del tablero 15
  1. Crear tablero 15 · KPI global DOTA.
  2. 3 visuales tipo "KPI" (cada uno muestra un número grande):
    • KPI 1: CONTAR_SI(_BARRIDA_ <> NULL) → "Conciliadas".
    • KPI 2: CONTAR_SI(_BARRIDA_ = NULL) → "Pendientes".
    • KPI 3: KPI1 / (KPI1 + KPI2) * 100 → "% eficiencia".
  3. Verificación: KPI 15 (conciliadas) debe ser igual a SUMA de #partidas del tablero 14. Si no cuadra, hay error en alguna barrida.
